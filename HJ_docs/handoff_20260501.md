## 잠재적 문제점 / 사용자 사전 인지 사항

### Problem 1: prediction msg 의 N 이 우리 N (=20) 과 다른 케이스
- 우리 NLP horizon N=20.
- predictor (`3d_opp_prediction.py`) 의 publish 가 N=20 timestep 일 거라 가정.
- **다를 가능성** — 코드 진입 첫 10분에 직접 확인.
  ```bash
  rostopic echo -n 1 /opponent_prediction/obstacles | head -50
  ```
  obstacles 배열 길이 확인.
- 다르면 Phase 1 spec 의 tail 처리 (M < N+1) 가 정확히 발동.

### Problem 2: tracking 의 obs.id 가 prediction msg 의 id 와 다를 가능성
- spec 의 매칭 알고리즘은 (s, d) 거리 기반. id 의존 X.
- 그러나 매칭 정확도 확인 필요 (tick_json `obs_horizon_source` 의 `tanchor:T?+P?` 비율).

### Problem 3: 정적 obstacle 의 prediction msg 동작
- predictor 가 정적 obs 도 publish 하는지 확인. 안 하면 spec 의 정지 가정 fallback 으로 처리됨.

### Problem 4: solver / NLP 의 corridor / bubble 함수가 obs_arr 의 timestep 의존성 가정 변화
- 현재 frenet_kin solver 는 obs_arr 가 timestep 별 다른 (s, d) 를 가지면 어떻게 동작?
- 코드 확인: `planner/mpc_planner/src/frenet_kin_solver.py` 의 `_build_corridor_bounds` 가 obs_arr 를 어떻게 사용하는지.
- 이미 `(N+1, 3)` shape 받아 timestep 별 처리하는지, 아니면 첫 row 만 보는지 — 진입 시 5분 grep 으로 확인.

### Problem 5: dual publisher (recovery_spliner) 영향
- 이전 세션 분석에서 `3d_mpc_headtohead.launch` 는 recovery_spliner 비활성. Phase 1 작업과 무관.
- 단 다른 launch 사용 시 영향 가능 — 확인.
