## 컬럼 정의

분석 스크립트는 토픽별로 다음을 계산:

- `n` : 메시지 수
- `totMB` : 재직렬화한 총 바이트 (MB)
- `avgKB` : 메시지당 평균 바이트 (KB)
- `Hz` : `1000 / dt_mean_ms` (실측 평균 인터벌 기반, 이름값과 다를 수 있음)
- `dt_ms / dtsd / dt_p95` : 메시지 간 인터벌 평균 / 표준편차 / 95퍼센타일 (ms) — **지터 지표**
- `lat_mn / lat_p95 / lat_mx` : `bag_record_time - msg.header.stamp` (ms) — **header 기반 지연 지표**. header가 없거나 비어있는 토픽은 공란.

> ⚠️ `lat_*` 해석 주의: bag을 record한 노드의 wall clock과 publish 노드의 `header.stamp` 가 **다른 시계**를 쓰면 절대값이 의미 없음. 아래 "타임베이스 이상" 섹션 참고.

## TL;DR — 다음 세션이 알아야 할 결론 5가지

1. **PointCloud2 7~9개가 전체 트래픽의 ~75%**. `/rslidar_points`(815MB) + `/glim_ros/*points*` 시리즈(각 ~118–230MB). LiDAR 분석/SLAM 디버깅이 아니면 다른 bag에서는 미수록 권장.
2. **`/relay/*` prefix 가 `/glim_ros/*`, `/local_waypoints/*`, `/state_*` 등 거의 모든 시각화 토픽을 2배로 복제**. RViz/Foxglove 원격용으로 보이지만 record까지 들어가서 대역폭/디스크 낭비. 다음 bag 기록 전에 `rosbag record --regex` 화이트리스트로 잡거나 relay 해제 후 record 권장.
3. **GLIL/`glim_ros` 계열 odom/pose의 `header.stamp` 가 record time보다 ~36.8s 앞섬**. 즉 header lat이 ~37000ms로 일관되게 큼. → 이건 실제 지연이 아니라 **GLIL 내부 시계와 시스템 wall clock이 ~37초 어긋난 상태로 publish됐다**는 뜻. Cross-topic 정렬할 때 `header.stamp` 신뢰 금지, 아니면 offset(약 -36.85s) 빼고 사용.
4. **VESC 계열은 깨끗함**: `/vesc/odom`, `/vesc/sensors/imu`, `/vesc/sensors/core` 모두 50Hz steady, header lat 0.2–0.8 ms, dt 표준편차 ~1ms 이하. 제어/저수준 디버깅 baseline으로 신뢰 가능.
5. **상위 레벨 plan/state 토픽 (state_machine, behavior_strategy, local_waypoints) 80Hz steady, p95 ~17ms, header lat 2–6ms** — 정상. recovery wpnts만 40Hz로 한 단 낮음(`p95 41ms`).

## 2. Hz / 지터 등급

평가 기준 (HJ 운용용 휴리스틱):
- **A (steady)** : `dt_std < 0.1*dt_mean` AND `dt_p95 < 1.3*dt_mean`
- **B (acceptable)** : `dt_p95 < 2*dt_mean`
- **C (jittery)** : `dt_p95 >= 2*dt_mean` 또는 `dt_std > 0.5*dt_mean`

| 등급 | 대표 토픽 | 비고 |
|---|---|---|
| A | `/vesc/odom`, `/vesc/sensors/imu`, `/vesc/sensors/core`, `/joy`, `/rslidar_imu_data`, `/rslidar_points`, `/lookahead_point`, `/state_machine`, `/state_marker`, `/behavior_strategy`, `/local_waypoints`, `/planner/avoidance/static_otwpnts`, `/planner/start_wpnts`, `/global_waypoints/*` (2 Hz steady) | 운영 신뢰. baseline 비교용으로 쓰기 좋음 |
| B | `/glim_ros/{raw_aligned_points,points,aligned_points}`, `/local_waypoints/markers` (159.9Hz), `/planner/recovery/markers`, `/relay/local_waypoints/markers` | jitter 있지만 plan/제어용으론 OK |
| C | `/glim_ros/*_corrected` 시리즈 (PC2/odom/pose 모두), `/glim_ros/base_odom` & `/car_state/odom` (76.6Hz target이지만 dt_std ~21ms, p95 42ms), `/tf` (dt_std 47ms vs mean 33ms), `/vesc/low_level/ackermann_cmd_mux/output` (dt_std 53.8ms — 가끔 큰 갭), `/rosout`/`/rosout_agg` | **localization/cmd 쪽 지터 주의**. 제어 루프가 76Hz odom 가정이면 가끔 42ms 갭 동안 stale state를 쓰는 셈 |

**핵심 우려:**
- `/glim_ros/base_odom` ↔ `/car_state/odom` 두 줄 모두 dt_p95=42ms. 이건 **제어 주기(50–80Hz)와 같은 자릿수의 stale window**. MPC/Sampling 노드에서 odom을 trigger로 쓰면 가끔 25ms 짜리 dropout이 들어옴. 컨트롤러는 보통 wall-clock timer라 영향 없지만, **plan validity 체크에서 odom timestamp를 보면 헷갈릴 수 있음**.
- `/vesc/low_level/ackermann_cmd_mux/output` dt_std 53.81ms — mean 21ms 인데 표준편차가 mean의 2.5배. 즉 가끔 100ms+ 출력 갭. 차량이 그동안 마지막 명령 hold 하는 구간 존재. mux 입력 노드 race일 가능성.

## 3. Header 기반 지연 (`bag t - header.stamp`)

대부분 토픽은 0–30ms 사이로 정상. 다음만 비정상:

### 3.1 GLIL/`glim_ros` 시계 오프셋 (~36.8 s)

| Topic | lat_mean (ms) | lat_p95 (ms) | lat_max (ms) |
|---|---:|---:|---:|
| `/rslidar_points` | 36865 | 36866 | 36869 |
| `/rslidar_imu_data` | 36755 | 36756 | 36757 |
| `/glim_ros/base_odom` | 36784 | 36848 | 36906 |
| `/car_state/odom` | 36787 | 36850 | 36907 |
| `/glim_ros/imu_odom` | 36783 | 36847 | 36906 |
| `/car_state/odom_frenet` | 36789 | 36855 | 36922 |
| `/glim_ros/{points, aligned_points}` | 36878 | 36883 | 36902 |
| `/glim_ros/*_corrected` | 36916 | 36971 | 36998 |

→ 일관되게 **약 36.85초 만큼 header.stamp 가 record time보다 과거**. 이건 LiDAR/GLIL 노드가 자기 내부 클럭(혹은 lidar 하드웨어 stamp)으로 stamp 찍은 결과. **실제 지연이 아니라 시계 오프셋**.

**다음 세션 활용 시 처리법:**
- 단일 토픽 내 시계열 분석은 `header.stamp` 차이로 OK.
- 두 토픽 간 정렬할 때는 **둘 다 GLIL 계열이면** OK, **GLIL ↔ VESC/wall-clock** 비교는 한쪽에 +36.85s 보정 필요. `/car_state/odom` 도 GLIL 시계라는 점 잊지 말 것 (controller_manager 가 GLIL base_odom 을 그대로 republish 하고 있음).
- "실시간 처리 지연이 36초"가 아니라는 점을 분석 도구가 헷갈리지 않게 주석 달아둘 것.
- 이 오프셋은 보통 LiDAR 드라이버에서 PTP/GPS 시각 동기화가 안 됐거나, GLIL이 ROS time 대신 lidar hardware time을 쓰면 발생. 추후 조사 항목.

### 4.2 LiDAR raw + corrected 동시 보존

- `/rslidar_points` (raw) 815MB
- `/glim_ros/raw_aligned_points` (lidar frame → world) 230MB
- `/glim_ros/raw_aligned_points_corrected` (loop-closure 후 보정) 230MB
- `/glim_ros/points` / `points_corrected` (deskewed 버전) 119MB ×2
- `/glim_ros/aligned_points` / 그 corrected 119MB ×2

→ 동일 데이터의 5단계 가공본을 다 들고 있음. 분석 목적별로:
- 외부 perception 디버깅: `/rslidar_points` 1개면 충분
- SLAM 결과 시각화: `/glim_ros/aligned_points_corrected` 1개면 충분
- 둘 다 필요한 경우만 2개 record

### 4.3 markers의 dual rate

`/local_waypoints/markers` 159.9 Hz vs `/local_waypoints` 본체 80 Hz, `/local_waypoints/vel_markers` 80 Hz. 본체 1번 publish에 markers 2번 들어가는 구간이 있다는 뜻. publisher 중복 또는 delete-then-add 패턴. 실시간 영향은 없지만 디스크 낭비. (marker publish 노드 위치 확인은 다음 세션.)
